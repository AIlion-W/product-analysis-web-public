# 内功问诊 Web 版设计

## 1. 设计结论

把现有独立「评价区全盘分析」入口替换为「内功问诊」，复用当前 `product-analysis-web` 的单页框架、服务器端密钥管理和下载能力，但不沿用旧模块「一次上传全部资料、一次模型调用、返回 Markdown」的处理方式。

新版采用「浏览器解析 + 分批语义分析 + 代码确定性计算 + 结构化问诊看板」架构：

1. 浏览器解析标准 Excel，压缩评价页截图并建立产品数据包。
2. 用户先确认产品归属、工作表映射、字段映射、有效行数和数据缺口。
3. 评价、问大家、前 20 六维和截图识别按产品分批调用模型。
4. 查重、完整性门禁、聚合计算、截断记账和证据链校验由代码完成。
5. 结果保存在当前浏览器内存，不写数据库，不保存历史。
6. 最终展示六分区问诊看板，并下载独立 HTML 和可审计 Excel。

首版只替换独立评价区入口。「全链路分析」继续使用现有通用评价区逻辑；待独立模块通过真实业务验收后，再单独设计全链路集成。

## 2. 目标

- 把 `neigong-wenzhen-v4` 的方法转成可重复、可复算、可追查的网页流程。
- 支持 1 份我方产品数据包和 0–3 份竞品数据包；有 1–3 个竞品时形成竞品对照，0 个竞品时只做我方诊断。
- 数据不足时明确降级，不用模型硬凑结论。
- 每条 action 回指 finding，每条 finding 回指 evidenceId，evidenceId 可定位到数据源、聚合项或原始行。
- 让运营在正式调用模型前看见上传识别结果，避免传错资料后浪费调用费用。
- 生成网页、HTML 和 Excel 三种一致结果。

## 3. 明确不做

- 不新增账号、权限、数据库、历史项目、后台管理或团队协作。
- 不做淘宝、天猫链接自动采集，不处理登录、验证码和反爬。
- 不把新问诊流程接入首版「全链路分析」。
- 不支持任意格式的评价表；首版只支持约定的标准 Excel。
- 不把全部计算交给模型，不以模型自报的行数、比例或重复率作为事实。
- 不把 HTTP 200、构建成功或页面可打开当作业务验收通过。

## 4. 输入模型

### 4.1 产品数据包

页面固定展示一张「我方产品」卡片，并允许动态添加最多三张竞品卡片。每张卡片包含：

```text
产品数据包/
├── 评价数据.xlsx
│   ├── 默认排序评价
│   └── 时间排序评价
├── 问大家.xlsx
└── 评价页截图.png
```

我方和竞品使用同一套解析规则。用户必须在分析前确认每份数据包的产品归属。系统不得只凭文件名静默猜测归属。

### 4.2 评价 Excel

必需工作表：

- `默认排序评价`
- `时间排序评价`

两张表使用同一列结构。首版接受下列标准列名；`序号` 与 `排名` 可作为同义字段，其余字段不自动模糊猜测：

- 序号／排名
- 用户昵称
- 评价时间
- 评价类型
- SKU
- 初评内容
- 追评内容

处理规则：

- 默认排序和时间排序必须分表，不能把两类数据混在一张表中。
- 以工作表原始顺序和序号字段共同保留平台排名；二者冲突时阻断分析并要求用户确认。
- 每张表最多使用排名靠前的 100 条，超出部分计入 `excludedOverLimit`。
- 空白行、缺少初评内容的行和无法确定排名的行进入 `excludedRows`，不得静默丢弃。
- `.~` 开头的 Excel 临时锁文件自动忽略，并写入 warnings。

### 4.3 初评与追评

- 一条评价始终算一行，不把追评拆成第二条评价。
- 初评是主评价正文，用于默认／时间排序的 NFKC 精确查重。
- 追评是补充上下文，参与评价类型和六维判断。
- AI 返回的证据必须注明来自初评还是追评。
- 追评为空不影响该行有效性。
- 纯数字、占位符或类似 `12` 的低信息追评不参与语义加分，但原值仍保留以便复核。

### 4.4 问大家 Excel

标准列名：

- 昵称
- 时间
- 问题
- 问答

处理规则：

- 按工作表原始顺序生成排名。
- 最多使用前 100 条。
- 问题为空的行排除；问答为空仍可保留问题，但标记回答缺失。
- 问答只作为上下文，不替代问题本身的主题分类。

### 4.5 评价页截图

截图用于提取和佐证：

- 商品名称或页面身份。
- 评价总量、好评人数等页面元数据。
- 评价标签及标签数量。
- 问大家总量。
- 页面上可见的前排内容证据。

截图不能代替默认排序或时间排序的 100 条评价明细。右侧标签截断、截图不完整或 OCR/视觉识别失败时，标签来源标记为 `partial` 或 `missing`，不得补造未显示标签。

## 5. 完整性门禁

评价与问大家统一使用以下状态：

- `complete`：有效且实际使用 100 条。
- `provisional`：有效且实际使用 90–99 条；可以分析，但结论必须显示样本不足。
- `insufficient`：有效且实际使用 1–89 条；保留逐条结果，不输出依赖该来源的正式结论。
- `missing`：0 条。

评价标签截图使用：

- `complete`
- `partial`
- `missing`

三类核心结论的最低依赖：

- F01「评价展示倾向」：我方默认排序和时间排序评价均至少 90 条。
- F02「默认前 20 六维体检」：我方默认排序评价至少 20 条。默认表有 90–99 条时，正式结论标为 `provisional`；低于 90 条时只保留逐条体检，F02 正式结论标为 `unavailable`，不进入正式总判断。
- F03「问大家对照」：我方问大家至少 90 条；每个参与正式对照的竞品问大家至少 90 条。

竞品数量不再写死：

- 0 个竞品：只做我方诊断。
- 1 个竞品：一对一对照。
- 2–3 个竞品：多竞品对照。
- 某个竞品未达门禁，只排除该竞品的正式对照，不阻断其他竞品。

## 6. 处理边界

### 6.1 必须由代码处理

- Excel 文件、工作表和字段解析。
- 排名、有效行、排除行、截断行统计。
- NFKC 归一化与去空白。
- 单表内部重复和默认／时间表多重集精确匹配。
- 类型数量、占比差、六维覆盖率和问题主题占比。
- `complete/provisional/insufficient/missing` 判定。
- rowId、sourceId、evidenceId 生成。
- action → finding → evidenceId 的引用完整性。
- 网页、HTML 和 Excel 数字一致性。

### 6.2 只由 AI 处理

- 每条评价的 t1–t8 单一主类型及原文证据。
- 默认前 20 条的人设、场景、痛点、细节、效果、爽点判断及逐维证据。
- 每条问题的 q1–q8 单一主题及原文证据。
- 截图中的标签和页面元数据识别。
- 基于已校验聚合结果形成 F01–F03 文字结论。
- 基于 finding 和 evidence 形成最多 8 条 P0–P2 动作。

模型不得自报或覆盖最终行数、重复率、占比、完整性状态和证据链校验结果。

## 7. 规范化与查重

查重主文本只使用初评内容：

1. Unicode NFKC 归一化。
2. 删除全部 Unicode 空白字符。
3. 保留其他字符，不做同义改写、错别字纠正或模糊匹配。
4. 单表内部按规范化全文建立重复组。
5. 默认与时间表使用一对一多重集匹配，不能把同一条默认评价重复匹配给多条时间评价。

查重输出必须包含匹配对的 rowId、分母、匹配数和重合率，确保可以独立复算。

## 8. 页面流程

### 8.1 第一步：上传资料

- 用户选择独立「内功问诊」入口。
- 上传我方数据包。
- 添加 1–3 个竞品卡片并分别上传数据包。
- 文件选择后不立即调用模型。

### 8.2 第二步：完整性检查

页面展示：

- 产品归属。
- 已识别文件及其角色。
- 工作表和字段映射。
- 每个来源的读取行数、有效行数、使用行数、排除数和截断数。
- 截图标签完整或截断状态。
- 阻断项、警告项和可降级项。

只有用户确认映射结果后，才能开始分析。

### 8.3 第三步：分批分析

- 默认评价、时间评价和问大家默认每 50 条一个批次。
- 每个产品的前 20 六维和截图元数据分别作为独立任务。
- 浏览器最多并发两个任务。
- 单批失败自动重试一次。
- 自动重试仍失败时停在进度页，允许手动重试或排除该竞品。
- 已完成结果保留在当前浏览器内存，不因单批失败重跑。
- 页面注册 `beforeunload` 提醒；刷新或关闭后本次状态丢失。

### 8.4 第四步：问诊看板

看板保留六个分区：

1. 数据完整性与产品对照。
2. 评价类型与前端展示倾向。
3. 默认前 20 六维体检。
4. 问大家对照分析。
5. 分析结论。
6. 落地清单。

所有缺失结果必须显示空态或 `unavailable`，不能隐藏数据缺口。

## 9. 前端与后端架构

### 9.1 前端职责

- 标准 Excel 读取和字段映射。
- 截图压缩。
- 产品卡片和文件归属管理。
- 完整性预检与确认界面。
- 批次切分、最大并发 2、重试和进度状态。
- 当前会话内的 `ProductPack[]`、批次结果和最终 `ReportData` 状态。
- React 问诊看板。
- 独立 HTML 和 Excel 导出。

前端不得使用 localStorage、IndexedDB 或其他持久化保存报告历史。

### 9.2 后端职责

新增独立 Route Handler：

```text
POST /api/neigong/analyze
```

请求通过 `task` 区分：

- `review-taxonomy`
- `question-topic`
- `top20-dimensions`
- `screenshot-metadata`
- `synthesis`

后端对每个任务重新校验 JSON 输入，选择对应提示词和严格 JSON Schema，调用 Responses API，并返回结构化结果或可识别错误码。

所配置的模型服务必须兼容 Responses API 的严格 JSON Schema 输出。若服务不支持或返回不符合 Schema 的结果，任务应明确失败并进入重试／人工处理流程，不回退到 Markdown 解析。

现有 `/api/analyze` 保持服务市场、竞品、详情页、买家秀和全链路模块。首版不把内功问诊任务塞入旧路由。

## 10. 数据协议

统一顶层对象：

```text
ReportData
├── meta
├── products
├── sources
├── taxonomy
├── topics
├── reviews
├── reviewTags
├── questions
├── top20
├── aggregates
├── findings
├── actions
├── legacy
├── excludedRows
├── errors
└── warnings
```

网页版统一使用：

- `reviews[].sort`
- `reviews[].typeId`
- `reviews[].typeEvidence`
- `reviews[].initialText`
- `reviews[].followupText`

不得同时保留模板旧字段 `primaryType`、`taxonomyEvidence`。完整性状态也统一为本设计第 5 节的四态，解决原 Skill 数据结构文档与 HTML 模板字段漂移。

项目实现时新增 `SOURCE_OF_TRUTH.md`，明确网页版的数据协议、业务规则、提示词和产品知识文件位置；网页运行时不能依赖部署环境之外的 `~/.codex/skills` 路径。

## 11. 失败与降级

允许降级继续：

- 截图识别失败：标签及截图元数据标为 unavailable。
- 单个竞品失败：用户确认排除后继续我方与其他竞品。
- 竞品数据低于 90 条：保留逐条结果，不进入正式对照。
- 模型拒绝或结构化输出无效：该批次不写入任何部分结果。

必须停止：

- 我方默认／时间评价工作表映射错误。
- 产品归属未确认。
- 同一 rowId 重复或来源锚点丢失。
- 聚合数量与逐条明细无法对账。
- action → finding → evidenceId 链条断裂。

## 12. 隐私与留存

- 应用不保存上传文件、解析数据、分析历史或报告。
- 浏览器刷新或关闭后状态消失。
- 模型请求保持 `store: false`。
- `store: false` 只表示应用请求不保存 Responses API 应用状态，不宣传为供应商层面的零数据留存；实际供应商留存取决于所用账号和服务策略。
- API Key 只保存在服务器环境变量中，不传到浏览器。

## 13. 导出

### 13.1 独立 HTML

- 包含当前 `ReportData`、样式和交互脚本。
- 离线打开可完整查看。
- 不包含上传原文件和 API Key。
- 与网页显示使用同一份经过校验的数据对象。

### 13.2 Excel

固定六张工作表：

1. 数据完整性
2. 评价逐条标注
3. 前 20 六维
4. 问大家逐条标注
5. 分析结论
6. 落地清单

Excel 必须保留 sourceId、rowId、findingId 和 evidenceId，不能只导出结论摘要。

## 14. 测试

### 14.1 解析与规则单元测试

- 缺少默认排序或时间排序工作表。
- 列名错误、空行、超过 100 条和 Excel 临时锁文件。
- 89、90、99、100、101 条门禁边界。
- 初评相同、追评不同的查重行为。
- NFKC、全角半角、空白和表情符号。
- 一对一多重集匹配。
- 排名字段与工作表顺序冲突。
- 纯数字和占位符追评。

### 14.2 模型契约测试

- 合法严格 JSON。
- 字段缺失、枚举越界、重复 rowId 和未知 rowId。
- 模型拒绝、超时、空输出和结构化输出失败。
- 分类证据不在初评或追评原文中。
- finding 引用不存在的 evidenceId。
- action 引用不存在的 findingId。

### 14.3 流程测试

- 0、1、3 个竞品。
- 单批自动重试和手动重试。
- 单个竞品排除后，其余结果不受污染。
- 截图截断或识别失败。
- 刷新前提示和刷新后状态清空。
- 网页、HTML 和 Excel 数字一致。
- 原市场、竞品、详情页、买家秀和全链路入口回归测试。

## 15. 业务验收

使用一组真实我方资料和至少一个真实竞品：

1. 人工核对每张表实际行数和排除原因。
2. 抽查至少 20 条评价分类及证据原文。
3. 独立复算默认／时间排序重合数。
4. 检查缺失数据是否正确显示 `unavailable`。
5. 从每条 P0 动作反查 finding、evidenceId 和原始评价或问题。
6. 对比网页、HTML 和 Excel 的数量、比例和状态。
7. 验证一个竞品失败时其他竞品仍能完成。
8. 在通过受控真实输入和人工复核前，不宣称业务验收完成。

现有本地只读样例可用于验证当前字段解析和问大家 100 条门禁，但它只有一张评价工作表，不能用于验收默认／时间排序对照。首次正式验收必须补齐默认排序评价和时间排序评价两份独立标准 Excel。

## 16. 实施顺序

1. 建立网页版真源、统一类型与严格 JSON Schema。
2. 实现标准 Excel 解析和完整性预检。
3. 实现确定性规则引擎与证据链验证。
4. 实现分批模型任务和失败恢复。
5. 实现 React 看板。
6. 实现 HTML 与六工作表 Excel 导出。
7. 完成自动化回归和真实样例验收。
